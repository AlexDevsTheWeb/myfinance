# Phase 1 Analysis — Secure the Data

> Part of Go-to-Market [#138](https://github.com/AlexDevsTheWeb/myfinance/issues/138)
> Phase 1: Weeks 2-3 — Architectural hardening to prevent data loss before beta.

---

## Overview

Phase 1 addresses three architectural weaknesses that threaten data integrity:

1. **Transactions stored as array in single Firestore doc** — 1 MiB limit, full rewrites, no pagination
2. **PAC state in localStorage** — lost on browser clear, no cross-device sync
3. **Recurring transaction race condition** — duplicate generation on concurrent snapshots

---

## 1.1 Migrate Transactions to Sub-collection

### Problem

`users/{uid}` is a single Firestore doc with all user data crammed into array fields. Transactions are stored as `transactions: ITransaction[]` in the `UserDoc` interface (`src/lib/converters.ts:6-29`). Every mutation (`addTransaction`, `updateTransaction`, `deleteTransaction`) rewrites the **entire** transactions array via `updateDoc(docRef, { transactions: sanitizedTransactions })`.

### Current Write Pattern (useFinanceStore.ts)

```
addTransaction → validate → optimistic update (Zustand) → sanitize ALL transactions → updateDoc({ transactions })
updateTransaction → map → optimistic update → sanitize ALL → updateDoc({ transactions })
deleteTransaction → filter + optimistic → sanitize ALL → updateDoc({ transactions })
```

### Risks

- **1 MiB limit** — a user with thousands of transactions + all other data (investments, budget, car, etc.) can hit the limit
- **Atomicity** — a single bad transaction write corrupts the entire array
- **No pagination** — Firestore can't do `limit()` + `startAfter()` on array fields
- **Cost** — every write charges for the full document size, not just the changed field
- **Concurrent writes** — two tabs open = last writer wins, losing data

### Solution Design

#### Target Schema

```
users/{uid}                         ← keep this doc, remove transactions field
├── profile: { ... }                ← existing fields minus transactions
├── recurringTransactions: [...]     ← keep (small, rarely written)
├── deletedRecurringInstances: [...] ← keep
├── accounts: [...]                  ← keep
├── categories: [...]                ← keep
├── brokerAccounts: [...]            ← keep
├── ...                              ← all other fields stay
│
├── transactions/{txnId}             ← NEW: sub-collection
│   ├── id: string
│   ├── date: string (YYYY-MM-DD)
│   ├── description: string
│   ├── amount: number
│   ├── type: 'expense' | 'income'
│   ├── accountId: string
│   ├── categoryId: string
│   ├── recurringLinkId?: string
│   └── createdAt: Timestamp
│
├── portfolio_history/{snapshotId}   ← existing sub-collection
├── dividends/{entryId}              ← rules exist, not used
└── tax_events/{eventId}             ← rules exist, not used
```

### Migration Strategy

1. **Phase A: Dual-write** — write to both array (legacy) and sub-collection (new). Reads still come from array.
2. **Phase B: One-time backfill** — script copies existing array transactions to sub-collection.
3. **Phase C: Flip reads** — `useSyncFinance` and all readers switch to sub-collection listener.
4. **Phase D: Remove legacy** — drop array field from `UserDoc` after confirming all users migrated.

### Files to Modify

| File | Change |
|------|--------|
| `src/lib/converters.ts` | Remove `transactions` from `UserDoc` interface, add converter for sub-collection |
| `src/store/useFinanceStore.ts` | Rewrite `addTransaction`, `updateTransaction`, `deleteTransaction`, `setTransactions` to target sub-collection |
| `src/hooks/useSyncFinance.ts` | Add `onSnapshot` listener on `users/{uid}/transactions/{txnId}` instead of reading from user doc |
| `src/store/types/finance.types.ts` | Add `TransactionDoc` type with server timestamps |
| `firestore.rules` | Add rules for sub-collection reads/writes |

## 1.2 Move PAC State from localStorage to Firestore

### Problem

PAC automation uses a split-state approach:

| State | Location | Persistence |
|-------|----------|-------------|
| `pendingPacTransaction` | Zustand memory (InvestmentStore) | Lost on refresh (regenerated by hook) |
| `lastPacGenerationDate` | Zustand memory (InvestmentStore) | Lost on refresh |
| `pac_last_{brokerId}` | localStorage | Persists across sessions but NOT across devices |

If a user clears browser data or switches device, the PAC hook re-generates pending transactions from scratch — potentially creating duplicates.

### Current Flow (usePacAutomation.ts)

1. On mount, iterate each broker with `monthlyPacAmount > 0`
2. Check `localStorage.getItem('pac_last_' + broker.id)` against `currentMonthKey`
3. If no match (or browser cleared), call `addPendingPacTransaction()`
4. `addPendingPacTransaction` sets `pendingPacTransaction` in Zustand memory
5. User confirms via `PacConfirmationDialog` → calls `confirmPacTransaction`
6. `confirmPacTransaction` writes the ETF transaction to Firestore but **does NOT persist `lastPacGenerationDate`**

### Key Code Locations

- `src/hooks/usePacAutomation.ts` — reads/writes localStorage at lines 46-49, 67
- `src/store/useInvestmentStore.ts` — `pendingPacTransaction` (line 20), `lastPacGenerationDate` (line 21), `confirmPacTransaction` (line 445)
- `src/components/investment/PacConfirmationDialog.tsx` — confirmation UI

### Solution Design

Add a `pacState` field to the `users/{uid}` document:

```typescript
interface PacState {
  lastGenerationDate: string;      // ISO date of last PAC generation
  pendingTransaction?: {
    brokerId: string;
    amount: number;
    date: string;
    status: 'pending' | 'confirmed' | 'executed';
  };
  perBrokerLastGeneration: Record<string, string>;  // brokerId → last month key
}
```

### Migration Path

1. Add `pacState` field to `UserDoc` interface
2. Update `usePacAutomation` to read from Firestore instead of localStorage on mount
3. Write `lastGenerationDate` after each PAC confirmation
4. Remove `pendingPacTransaction` from Zustand (now in Firestore)
5. One-time migration: read localStorage keys and write to Firestore

## 1.3 Fix Recurring Transaction Race Condition

### Problem

`checkRecurring()` (useFinanceStore.ts:789-875) is called from three sources without debouncing:

1. **`useSyncFinance` onSnapshot** (line 65) — every Firestore doc change
2. **`addRecurring()`** (line 752) — after creating a recurring template
3. **`updateRecurring()`** (line 781) — after editing a recurring template

The only guard is `if (state.isCheckingRecurring) return;` — a boolean flag that only prevents re-entrance within the same execution context, not concurrent calls from multiple tabs or rapid snapshot events.

### Race Scenario

```
onSnapshot A fires → checkRecurring A starts, reads transactions: []
onSnapshot B fires → checkRecurring B starts, reads transactions: []
  A generates txn T1, T2, writes [T1, T2] to Firestore
  B generates txn T1, T2, writes [T1, T2] to Firestore
```

Result: duplicates survive because B overwrote A's write with the same content (no net loss here), but interleaving with user writes can cause actual data loss.

### Solution Design

#### Firestore-side Dedup

Add a `generationLock` field to `recurringTransactions`:

```typescript
interface IRecurringTransaction {
  // ... existing fields
  lastGeneratedUpTo?: string;  // ISO date — last month/year that was generated
}
```

When `checkRecurring` runs, it reads `lastGeneratedUpTo` from each recurring template and starts generating from there. This is atomic because each update to the recurring doc updates `lastGeneratedUpTo` in the same write.

#### Session Debounce

Add a ref-based guard that prevents `checkRecurring` from running more than once per session:

```typescript
const recurringCheckRunRef = useRef(false);
// In onSnapshot callback:
if (recurringCheckRunRef.current) return;
recurringCheckRunRef.current = true;
checkRecurring();
```

This prevents redundant checks across re-renders and multiple snapshot events within the same session.

#### Enhanced Guard

Replace the simple boolean flag with a timestamp-based lock:

```typescript
lastRecurringCheck: string | null;  // ISO timestamp in store
// In checkRecurring():
const timeSinceLastCheck = Date.now() - new Date(state.lastRecurringCheck || 0).getTime();
if (timeSinceLastCheck < 5000) return;  // Min 5 seconds between checks
```

## Risk Assessment

| Item | Complexity | Risk | Priority |
|------|------------|------|----------|
| 1.1 Sub-collection migration | High | High (biggest change, data migration) | **P0** |
| 1.2 PAC state to Firestore | Medium | Medium (dual-state complexity) | **P1** |
| 1.3 Recurring race condition | Low | Low (small change, high safety impact) | **P1** |

## Recommended Order

1. **1.3 first** — smallest change, quick win, prevents data corruption during other changes
2. **1.2 second** — medium change, standalone, doesn't depend on 1.1
3. **1.1 last** — largest change, benefits from the stability gained by 1.2 and 1.3

## Known Dependencies

- All three items modify `useFinanceStore` and `useInvestmentStore` — sequential implementation to avoid merge conflicts
- Item 1.1 must coordinate with `useSyncFinance`, `useInvestmentSync`, and `useBudgetSync` — all currently share the same user doc listener
- Item 1.2 depends on `PacConfirmationDialog` component and `usePacAutomation` hook — both well-defined
