# Implementation Report — Utilities & Consumption page

**Branch:** `feat/utilities-consumption-page` · **PR:** [#202](https://github.com/AlexDevsTheWeb/myfinance/pull/202) · **Status:** shipped

## Context

The request was a prompt dropped in `docs/raw/2026-11-23-utilities/` describing a
full **Utilities & Consumption** page in the Executive Dark / Swiss-Tech system
used by the dashboard, the transaction ledger (PR #197) and settings (PR #201).

The page it replaced was a two-tab electricity/gas view: four cards, a history
table and a single line chart. It had no water support, no cross-utility view, no
fixed-vs-energy split, no unit-rate weighting and no Year-over-Year comparison.
It also read `category === 'Bollette'` and `subcategory === 'Elettricità'`
literally, so the English UI and renamed categories produced an empty page.

The prompt assumed utility fields (`kwh`, `smc`, `waterM3`, `fixedFee`,
`energyFee`) that did not exist. Its own execution workflow asked for exactly
that inspection before implementing.

## Review follow-up (2026-11-23)

The first cut exposed three controls that opened the same drawer on `/utilities`:
the TopBar CTA, the new page button and the floating action button. In review the
decision was to keep **one** create action:

- The page-local `+ Nuova Bolletta / Lettura` button was removed.
- The FAB was removed globally; its feature page is now marked deprecated.
- The TopBar CTA remains and, on `/utilities`, seeds the bill category and
  expands the utility block. Both desktop and mobile call the same
  `useNewTransaction()` hook, so the preset logic exists once.
- Because the TopBar is not rendered below 900px, the mobile header keeps an
  identical `+` icon button. Removing the FAB without this would have left mobile
  with no create action outside the dashboard.

## Decisions

1. **Optional additive schema, not a migration.** All five fields are optional
   and absent means "unknown". Existing documents load unchanged; the page
   classifies them from category/subcategory keywords. A required field or a
   backfill would have blocked every existing user's page until it completed.
2. **One `utilityType` instead of three volume fields.** `kwh`, `smc` and
   `waterM3` would be three names for the same reading and would each need
   validation, sanitisation, converter and backup handling. The existing
   `consumption` number plus the kind (which selects the unit) is one value with
   one persistence path.
3. **Split is derivable from one quota.** Bills often show only the fixed fee or
   only the energy component. Deriving the other from the total keeps the stacked
   bars equal to the spend; requiring both would leave gaps in real data.
4. **Weighted unit rate.** Period spend ÷ period volume. Averaging per-bill rates
   over-weights small bills and drifts from what the meter actually cost.
5. **KPI cards ignore the utility filter; the analysis honours it.** The four
   cards are the period's breakdown, so selecting *Luce* does not blank the gas
   and water cards. Charts and table narrow as expected.
6. **The consumption line disappears in the mixed view.** kWh, SMC and m³ cannot
   share an axis. Bars stay in EUR (where a mixed stack is meaningful); the line
   returns as soon as one utility is selected.
7. **One create action, not three.** The utilities page opens the global drawer
   through the shell (TopBar CTA / mobile header), never through a local button.
   `useNewTransaction()` owns the route-aware preset so desktop and mobile cannot
   drift. The FAB was removed for the same reason.
8. **i18n over the prompt's Italian literals.** The page is fully translated (it
   and en), including CSV headers, table headers and the YoY captions.
9. **Duplicate clears readings and quotas.** A copy is a template for the next
   bill: identity (supplier, meter, kind) survives, the paid bill's volume and
   amounts do not.
10. **No routing change.** `/utilities` and the module-gated sidebar entry
    already existed; the prompt's step 3 was already satisfied.

was to run the full loop autonomously. The two schema-level choices (optional
fields, one volume field) are the ones most worth revisiting if the product later
needs separate gas/water readings on one bill.

Defects caught during the work, before the PR:

- The first CSV builder inserted the unit column by splitting the serialized
  line on `;`, which breaks as soon as a field contains an escaped separator.
  Replaced with a single ordered row array.
- `period === 'all'` inside the YoY memo was flagged as an impossible comparison
  because the derived `yoyActive` flag already narrowed the type; the guard was
  restructured and the redundant flag removed.
- `sanitizeTransaction` uses `Number(...)`, so a legacy comma-decimal string
  would produce `NaN`; the test pins the supported string form (`'18.5'`) rather
  than pretending comma strings are handled. The drawer always stores numbers.

## Not verified / deferred

- **No browser pass.** Chart composition (`ChartsDataProvider` + `BarPlot` +
  `LinePlot`), the custom axis tooltip, the chart resize behaviour and the
  route-aware drawer preset were not exercised in a real browser. The new mobile
  header `+` is likewise untested outside typecheck and build. There is no E2E
  harness and MUI X charts are not rendered in jsdom tests. A manual check at
  desktop and mobile widths is still owed before merge.
- **No pixel comparison.** The prompt supplied no screenshot or HTML export,
  only a written spec, so fidelity is reasoned from the design tokens.
- **Water has no default subcategory for existing users.** The default list only
  applies to new accounts; existing users must add `Acqua` (or use any
  subcategory containing "acqua") before water bills classify.
- **Bills split across two utilities are not modelled.** One transaction belongs
  to one utility kind.
- **No chart for per-supplier comparison.** Not requested; the table covers it.
