# Implementation Report — Car & Fleet Analytics rebuild

**Branch:** `feat/car-fleet-analytics` · **PR:** [#204](https://github.com/AlexDevsTheWeb/myfinance/pull/204) · **Status:** shipped

## Context

The source document asked for a full rebuild of `/car` as a vehicle-scoped fleet
analytics page: header filters, four KPI cards, a dual-axis spend/cost chart, a
YoY distance chart, a dense expense ledger and a car block in the global drawer.

The existing page was 693 lines of Mileage/Tires/Fuel tabs with hardcoded Italian
months, legacy blue gradients and fuel detected by category name. There was no
vehicle concept, so efficiency and €/km were global and a scooter could dilute
the car's numbers.

Three decisions were agreed before implementation:

1. **Keep tires and manual mileage** in a collapsible secondary section.
2. **Identify vehicles with `vehicleName` + `vehicleType`**, not a registry.
3. **Add dedicated `liters` / `pricePerLiter`**, separate from utility `consumption`.

The document's `#0B0E14` shell colour is not the real token; the theme uses
`#0B0F17` (`apps/web/src/theme/theme.ts:57`). The page uses theme tokens.

## Review fix — empty metrics on existing data

The first build read distance only from the new `odometerKm` field. Existing
accounts keep their distance in the `carMileage` document field and their fuel
volume in `consumption`, so `/car` showed 0 km, “—” €/km, no efficiency and no
YoY comparison. This was a real product bug: the data existed, but the page did
not read it.

Fixed without changing the schema:

- **Distance fallback** — `legacyMileageSeries()` derives monthly distance from
  `carMileage` + `carInitialMileage`. It is used only while the untagged/main
  scope has no transaction-level odometer deltas, so it can never be added twice.
  An unset initial mileage (`0`) makes the first reading a baseline instead of a
  multi-thousand-km delta.
- **Litres fallback** — `fuelLitersOf()` uses `liters` first, then the legacy
  `consumption` field on fuel rows.
- **Default period** — `latestCarDataYear()` chooses the latest year with either
  transaction or manual-log data, so a 2025-only account is not empty in 2026.
- **Chart note** — while the fallback is active the charts say the distance comes
  from the manual log.
- **Tests** — 8 more `car.utils` tests (26 in that file, 334 overall).

## Decisions

- **`expenseType` is a stable enum** (`fuel | maintenance | tax`) and the labels
  are localised. Storing the Italian display strings would have frozen the
  language into the data and broken the English UI. This mirrors `utilityType`.
- **Distance comes from transaction odometer readings**, not the manual mileage
  log. The log is monthly and vehicle-agnostic, so using it would violate strict
  per-vehicle isolation. It stays as a separate maintenance tool.
- **The vehicle selector is data-driven.** The document's labels
  (`Auto Principale`, `Scooter / Moto`, `Noleggio / Viaggi`) are treated as
  example values; the real options are the names present in the data, plus
  `All` and `Unassigned`.
- **No page-level create CTA.** The previous review collapsed every create action
  into the TopBar CTA; `/car` is now one of its route-aware presets, so adding a
  second button would undo that decision.
- **Classification order is fuel → tax → maintenance** and explicit
  `expenseType` always wins. Utility bills are excluded before any keyword match.

## Deviations

1. **The PR number is assigned by GitHub**, not `#204` as the document says.
2. **Vehicle filter labels are data-driven**, not the four fixed names in the
   document. A type badge shows the class instead.
3. **`expenseType` values are enums**, not the Italian literals
   `Rifornimento` / `Tagliando` / `Bollo`. Labels are translated at render time.
4. **The dashed previous-year line is CSS**, not a series prop: MUI X v9 line
   series have no dash option, so `stroke-dasharray` targets
   `path[data-series="previous"]`. The muted colour is the primary cue, so the
   chart still reads correctly if the selector changes.
5. **"Maintenance / fixed fees" in the chart is "other car spend"** — every
   non-fuel vehicle expense (maintenance, tax, tolls, parking). The model has no
   separate fixed-fee field, and inventing one would duplicate `amount`.
6. **A year filter can include a cross-year delta** (a January fill measures
   distance since the previous fill, possibly in December). This is inherent to
   consecutive odometer readings and is documented on the feature page.
7. **`liters` does not replace `consumption`.** Utilities keep `consumption`;
   fuel uses `liters`. The drawer never shows both blocks at once.

## Not verified / deferred

- **No browser visual check.** The charts, the new drawer accordion and the
  responsive grid compile and are typechecked, but were not opened in a real
  browser in this environment.
- **No mobile screenshot.** The KPI grid and the table scroll are responsive by
  construction (`xs`/`sm`/`lg` breakpoints) but not visually verified.
- **The dashed-line CSS selector is unverified at runtime.** It targets the
  class/data attribute exposed by MUI X; if the class changes, the line is still
  distinguished by colour.
- **No real user data run.** The maths is covered by 26 unit tests with synthetic
  readings; untagged legacy rows are handled by design but were not exercised
  against a real Firestore export. The fallback reads `carMileage`,
  `carInitialMileage` and `consumption` exactly as the converters expose them.
- **No migration.** None is needed: every new field is optional and old documents
  read back unchanged.
- **No changes to Firestore rules** — the transaction subcollection rules already
  accept arbitrary fields for the owner.
- **CSV not opened in Excel.** Separator (`;`), decimal comma and BOM follow the
  existing utilities export.
