# Implementation Report — Add Transaction Drawer

**Branch:** `feat/add-transaction-drawer` · **PR:** [#199](https://github.com/AlexDevsTheWeb/myfinance/pull/199) · **Status:** shipped

## Context

Transaction entry was a centred `Dialog` (`components/modals/TransactionModal.tsx`)
rendered in two places with separate state: the global one in `Layout` driven by
`useUiStore`, and a local copy inside `TransactionsPage` for row editing. The
dashboard had its own CTA, and the global FAB expanded a two-button menu
(*New Income* / *New Expense*) rather than a form.

The request: one right-side drawer with three type tabs, a hero amount, and
progressive disclosure for utility consumption and recurrence.

Three decisions were confirmed with the user before coding:

| Question | Decision |
|---|---|
| Replace the modal everywhere? | Yes — one add/edit surface, modal deleted |
| Four typed consumption fields (`kwh`/`smc`/`liters`/`odometer`)? | No — reuse the existing generic `consumption`; odometer stays in the Car module |
| What does "set as recurring" save? | Today's transaction **and** a template starting next month |

## Changes

| Area | What changed |
|---|---|
| `components/transactions/AddTransactionDrawer.tsx` | New — drawer shell, tabs, hero amount, core fields, two accordions, footer |
| `components/transactions/transactionDrawer.utils.ts` | New — draft validation, utility-unit resolution, account balance, template mapping |
| `store/useUiStore.ts` | `txModal*` → `txDrawer*`, type widened to include `transfer`, actions renamed |
| `components/layout/Layout.tsx` | Two-button FAB replaced by a single circular FAB; renders `AddTransactionDrawer`; modal removed |
| `components/dashboard/TopBar.tsx` | CTA opens the drawer |
| `pages/TransactionsPage.tsx` | Row Edit opens the drawer; local modal state removed |
| `components/modals/TransactionModal.tsx` | **Deleted** — no dialog transaction form remains |
| `locales/{it,en}.json` | `transactions.drawer.*` block |

## Decisions

1. **The drawer is mounted once, in `Layout`.** Every trigger becomes a
   `openTransactionDrawer(type, transaction?)` call. This removes the duplicated
   modal state in `TransactionsPage` that could drift from the global one.
2. **A `Fab` component, not the previous two-button stack.** A single action is
   honest: the type is chosen inside the drawer, where the segmented tabs are the
   first thing you see.
3. **`DatePicker`, not `DateTimePicker`.** `ITransaction.date` is a `YYYY-MM-DD`
   string; accepting a time would be a UI promise the model cannot keep.
4. **`consumption` is reused with a dynamic unit.** It already feeds
   `useDashboardMetrics` (kWh and smc aggregates). Adding four typed fields would
   have required sanitization, converters, validation and a migration, and would
   have split one concept across five columns. Fuel stores litres in
   `consumption` and derives €/L from amount ÷ litres; the odometer remains a Car
   module concern because it is a monthly reading, not a transaction attribute.
5. **Recurring templates start on the 1st of next month.** Today's movement is
   already being saved; starting this month would make `checkRecurring` generate
   a duplicate on the next run.
6. **Editing never touches recurrence.** The block is hidden in edit mode and a
   note appears for generated instances, so a user cannot accidentally fork a
   template by editing one occurrence.
7. **Utility detection matches names, not ids.** Categories are user data with no
   stable id or type; the resolver matches known Italian and English terms across
   category + subcategory. It degrades to `null`, which simply leaves the
   accordion collapsed and optional.
8. **ConfigPage keeps `TransactionForm`.** Compilation surfaced that
   `ConfigPage` uses the old form with `isRecurring` for its advanced template
   manager. The drawer does not replace that screen, so the form file was
   restored unchanged rather than deleted.

**Compilation caught a wrong assumption:** the plan stated that no UI created
recurring templates today. `tsc` failed on `ConfigPage` importing the deleted
`TransactionForm`, which corrected it — ConfigPage has had a template editor all
along. The file was restored and the drawer's recurrence is documented as a
second, faster entry point rather than a first capability.

## Not verified / deferred

- **No browser interaction test.** There is no E2E harness; tab switching, the
  accordions, autocomplete back-filling and the drawer animation were exercised
  only through the unit tests of the pure helpers and the production build.
- **No visual check against the prompt.** It is a written spec with no export
  HTML, unlike the ledger prototype; fidelity is interpreted from the text.
- **No migration for existing consumption data** — not needed, since the field
  was reused unchanged.
- **Bimonthly recurrence** remains unsupported in the model; no workaround was
  invented.
- **Deferred:** destination-account transfer support, remaining-credit display on
  cards (plafond is shown instead).
